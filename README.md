# 快速开始

如果你第一次接触 `CF-EMBY-PROXY-UI`[**自用备份：revproxy**]，建议按下面顺序上手。

>  原作者：[@axuitomo](https://github.com/axuitomo)

## 第一步：先确认项目是否适合你

更适合：

- 多节点统一入口
- 需要隐藏源站 IP
- 希望要一个管理后台
- 想做 Cloudflare 边缘代理和分流

不太适合：

- 纯局域网 / 内网直连
- 源站已经在线路很好且不需要代理
- 大规模公共分享和超大流量分发

## 第二步：准备运行时资源

最低需要：

- 一个 Cloudflare Worker
- 一个 KV 绑定：`ENI_KV`
- 两个 Secret：`ADMIN_PASS`、`JWT_SECRET`

推荐同时准备：

- 一个 D1 绑定：`DB`
- 自定义后台路径：`ADMIN_PATH`
- 如果要启用域名前缀代理，再准备 `HOST`

## 第三步：选择部署方式

### 方式 A：控制台直接粘贴

适合先快速跑通环境，验证 Worker 是否能正常工作。

### 方式 B：Cloudflare 连接 GitHub 自动部署

适合后续按仓库提交触发重新部署，部署入口仍以根目录 `worker.js` 和 `wrangler.toml` 为准。

## 第四步：首次进入后台

部署成功后，优先验证：

1. `ADMIN_PATH` 能否正常打开后台
2. 登录是否成功
3. `ENI_KV` 是否可读写
4. 如果绑定了 D1，日志页是否能初始化数据库

## ⚙️ 环境变量与绑定配置指南

在部署本项目时，你需要配置相应的环境变量与服务绑定。为了方便管理，我们将配置项分为 **Worker 核心配置**（在 Cloudflare 控制台设置）和 **Web 面板进阶配置**（在部署后的管理后台设置）。

### 一、 Worker 核心配置（控制台填写）

在 Cloudflare Worker 的 设置 -> 变量和机密 或 绑定页面 中进行配置。建议首次部署时对照下表直接填写：

#### [必需项]

这些是系统正常运行的基础，**必须配置**。

| 变量名 / 绑定名称 | 类型 | 作用说明 | 配置示例 / 建议 |
| :--- | :--- | :--- | :--- |
| **`ENI_KV`** | KV 绑定 | **核心数据存储**。用于持久化保存项目主配置、节点信息、失败计数统计以及登录锁定状态等。 | 绑定你创建的 KV 命名空间（例如：`EMBY_DATA`）。 |
| **`ADMIN_PASS`** | 加密变量 (Secret) | **后台登录密码**。用于验证管理面板的访问权限。 | `MyStrongPassword123` |
| **`JWT_SECRET`** | 加密变量 (Secret) | **安全会话密钥**。用于生成和校验后台登录状态 (JWT)，防止越权访问。 | 建议填入一段高强度的随机长字符串。 |

####  [可选项]

按需配置，用于开启日志统计或自定义系统行为。『**建议添加**』

| 变量名 / 绑定名称 | 类型 | 作用说明 | 配置示例 / 建议 |
| :--- | :--- | :--- | :--- |
| **`DB`** | D1 绑定 | **日志数据库**。绑定后可开启请求日志审计、流量统计及自动化日报功能。 | 绑定你创建的 D1 数据库。 |
| **`ADMIN_PATH`** | 文本变量 (Var) | **自定义管理入口**。用于修改默认的 `/admin` 路径，有效防范自动化扫描工具的嗅探。 | `/secret_portal_99`<br>\> ⚠️ **注意**：不能以 `/api` 开头。 |
| **`HOST`** | 文本变量 (Var) | **域名前缀代理入口域名**。当你准备使用 `host_prefix` 节点、当前站点 DNS 草稿或基于当前域名的推荐回填时，需要提供一个标准入口域名。 | `emby.example.com`<br/>**注意：** 只做“当前站点是谁”的声明，不会自动帮你创建 DNS、路由或证书。 |
| **`LEGACY_HOST`** | 文本变量 (Var) | **旧版兼容入口域名**。升级到域名前缀代理时，用来声明“旧版本还在使用的对外域名”，让旧域名上的路径入口在迁移期继续兼容。『更换域名时使用』 | `emby.example.com`<br/>**注意：** 这是“旧入口是谁”的声明，不会自动帮你创建旧域名的 DNS、证书或路由；如果它和 `HOST` 相同，则基本等于没开。 |

> 💡 **命名兼容性提示**：
> 核心代码已向下兼容多种旧版命名（如 `KV` / `EMBY_KV` / `EMBY_PROXY` 会自动映射为 `ENI_KV`，`D1` / `PROXY_LOGS` 会映射为 `DB`）。但**强烈建议在新部署时统一使用 `ENI_KV` 和 `DB`**，以确保与后续的更新、README 说明及自动化脚本保持一致。

## 部署步骤

### 第一步：创建 KV

1. 打开 Cloudflare Dashboard
2. 进入**左侧导航栏>储存与数据库 > Workers KV**
3. 创建一个 命名空间，例如：`EMBY_DATA`

### 第二步：创建 Worker

#### Cloudflare 控制台直接粘贴

1. 进入 **Workers 和 Pages -> 创建应用 -> 从helloworld开始->设置名称创建**
2. 创建后进入 **Edit code**
3. 将 `worker.js` 全量替换进去并部署
4. 再到 Worker 的 **Settings / Compatibility** 中确认 `compatibility_date = 2026-03-13`，并启用 `enable_request_signal`

### 第三步：绑定 KV

1. 添加绑定选择KV 命名空间
2. 变量名填：`ENI_KV`
3. 绑定到你刚创建的 KV

### 第四步：创建并绑定 D1（可选但推荐）

1. 打开 左侧导航栏->储存与数据库 -> D1SQL数据库
2. 创建数据库，例如：`emby_proxy_logs`
3. 如果你使用的是方式 A，回到 Worker 绑定页，添加绑定选择D1 数据库
4. 变量名填：`DB`
5. 如果你使用的是方式 B 或方式 C，请把数据库名称和数据库 ID 填入 `wrangler.toml`，然后重新推送到已绑定分支触发自动部署
6. 后续在后台“日志记录”页面执行初始化 DB

> 如果你使用“方式 A：控制台直接粘贴”，KV / D1 仍然需要在 Cloudflare Dashboard 中手动绑定；如果你使用“方式 B / 方式 C”，则优先以 `wrangler.toml` 中填写的绑定信息为准。

### 第五步：设置环境变量

在 Worker 的 变量与机密 中新增：

- `ADMIN_PASS`：后台密码
- `JWT_SECRET`：随机高强度字符串
- `ADMIN_PATH`：可选，自定义管理后台入口，默认 `/admin`
- `HOST`：按需配置；只有启用域名前缀代理、当前站点 DNS 草稿或相关站点级功能时才必填

> 如果首次请求时缺少 `ADMIN_PASS` 或 `JWT_SECRET`，Worker 会在控制台打印一次初始化警告，首页和管理页也会显示“系统未初始化”提示。

### 第六步：按需添加 Cron Trigger

如果你需要自动清理日志、发送 Telegram 日报或定时异常告警，再补这一步：

1. 打开 Worker 的 **Triggers**
2. 添加一个 **Cron Trigger**
3. 使用每 1 小时一次的表达式：`0 */1 * * *` [也可以选择定时触发Worker，注意你的后台管理设置]
4. 保存后等待 Cloudflare 全球传播生效

> `0 * * * *` 表示按 **UTC 时区** 在每个整点执行一次，也就是每小时的第 `0` 分钟触发一次。

> Cloudflare 官方文档说明：注意Cron Trigger 使用 UTC，而中国时区是UTC+8,免费计划最多 5 个、付费计划最多 250 个；单次 Cron 执行最长 15 分钟。

> 当前版本里，Cron 触发后并不会无脑执行全部任务；Worker 会先结合 `scheduleUtcOffsetMinutes`、固定时段队列和运行时租约，判断当前是否真的轮到 DNS 自动上传、日报发送或异常告警执行。

# 域名前缀代理与进阶配置教程

本文档旨在详细解析域名前缀代理的核心参数及配置场景，帮助您快速完成域名优选加速，并实现后台管理面板的规范化绑定。

## 一、 核心参数概览

在开始部署前，需要在 Cloudflare 环境或面板中预先规划并配置以下核心参数：

1. **DNS 记录**：决定流量的入口与优选节点。
2. **路由 (Routes)**：定义 Worker 接管请求的流量范围。
3. **API 令牌 (Token)**：授权系统自动化管理解析记录。
4. **HOST / LEGACY_HOST**：界定业务主域并实现业务的平滑迁移。

------

## 二、 参数原理解析

### 1. DNS 记录 (节点优选加速)

- **配置逻辑**：需将**根域名**（Apex Domain）的 CNAME 记录指向您的“优选域名”或“优选 IP”，此记录将作为所有域名前缀节点的全局加速基准。
- **⚠️ 覆盖警告**：系统基于 API 运作，会自动将“域名前缀”对应子域名的 CNAME 指向根域。**请勿为子域名单独手动设置 CNAME 记录**，否则在后台面板编辑并保存节点时，您的自定义记录将被系统覆写。

### 2. 路由 (Routes)

为了让 Worker 完全接管根域名及前缀子域名的流量，必须严格配置通配符路由。以 `indevs.in` 为例，需**同时添加**以下两条规则：

| 路由规则                    | 匹配范围               | 命中示例                            | 未命中示例                                                |
| :-------------------------- | :--------------------- | :---------------------------------- | :-------------------------------------------------------- |
| **规则 A:** `indevs.in/*`   | 仅限根域名及其所有路径 | `indevs.in/api` `indevs.in/login`   | `www.indevs.in` (子域不匹配)                              |
| **规则 B:** `*.indevs.in/*` | 所有一级子域名及其路径 | `cdn.indevs.in` `v1.indevs.in/path` | `indevs.in` (根域不匹配) `a.b.indevs.in` (多级子域不匹配) |

### 3. API 令牌权限 (自动化管理)

- **配置要求**：系统依赖 Cloudflare API 自动创建和更新域名前缀节点。请确保在后台填入的 API 令牌具有操作该域名的绝对权限。
- **所需权限范围**：`区域 (Zone)` -> `DNS` -> `编辑 (Edit)`。

### 4. 环境变量：HOST 与 LEGACY_HOST

#### `HOST` (主干域名)

- **规范定义**：必须严格设置为您的**根域名**（如 `indevs.in`）。生成的域名前缀将以此为基础，作为一级子域名派生。
- **证书限制**：Cloudflare 免费版 (Universal SSL) 仅支持为“根域”及“一级子域名”签发证书。此参数可防止生成无效的跨级子域名证书。
- **安全入口**：配置后，出于面板接口的安全与规范考量，**仅允许**通过 `HOST` （或 `LEGACY_HOST`）设定的域名访问后台管理系统。

#### `LEGACY_HOST` (平滑过渡保障)

- **业务场景**：在更换主 `HOST` 域名时，为了避免客户端（如播放器、现有节点）中已填入的旧地址瞬间失效。
- **配置方案**：将旧的根域名填入 `LEGACY_HOST`。在 DNS 迁移和客户端配置更新的过渡期内，旧入口的访问与节点连接将继续保持畅通。

------

## 三、 实战部署演示

以下操作以根域名 `xyz9923.qzz.io` 为例，演示从零到一的完整绑定流程。

| 类型 | 目标值               |
| :--- | :------------------- |
| 路由 | `*.xyz9923.qzz.io/*` |
| 路由 | `xyz9923.qzz.io/*`   |

### 步骤 4：配置 Worker 环境变量

进入目标 Worker -> **设置** -> **变量和机密**，添加以下环境变量以完成面板握手。

| 纯文本 | `HOST`        | `xyz9923.qzz.io`                                 |

# Cloudflare Cache Rules 教程

这篇教程的目标很简单：让 Cloudflare 在边缘节点共享缓存同一个视频流，从而明显减少源站回源和带宽压力。

## 核心原理

Emby 播放视频时，URL 后面通常会带有用户级认证参数，比如 `?api_key=xxx&DeviceId=yyy`。默认情况下，Cloudflare 会把这些不同参数当成不同请求分别回源。

这里最关键的设置就是 **Ignore query string**。开启后，Cloudflare 会忽略问号后面的认证参数，把同一个视频路径缓存成一份共享内容，供不同用户复用。

## 配置步骤

### 第一步：进入 Cache Rules 配置页面

1. 登录 Cloudflare 控制台，点击进入你绑定了网关的域名。
2. 在左侧菜单栏中，依次展开 **Caching** -> **Cache Rules**。
3. 点击右侧的 **Create rule** 按钮。

### 第二步：配置匹配条件 (Expression)

这是为了告诉 Cloudflare 哪些请求是“大视频流”，需要被缓存。

1. 规则名称可以随便填，例如 `Emby Video Cache`。
2. 在 **When incoming requests match** 区域点击 **Edit expression**，切换到代码模式。
3. 将下面这段表达式直接粘贴进去：



```
(http.request.uri.path contains "/emby/videos/") or (http.request.uri.path contains "/Videos/") or (http.request.uri.path.extension in {"mp4" "mkv" "ts" "m4s"})
```

这段表达式的意思是：只要 URL 路径包含 `/emby/videos/`、`/Videos/`，或者文件后缀属于常见流媒体格式，就触发这条缓存规则。

### 第三步：设置缓存行为

往下滚动页面，配置具体的缓存动作：

1. **Cache eligibility** 选择 **Eligible for cache**，有些界面也可能显示为 `Cache everything`。

2. Edge TTL

   ：

   - 选择 **Ignore origin and use this TTL**
   - 时长可以先设成 **一个月**，后续再按你的需求调整

3. Cache key

   ：

   - 展开 **Query string** 设置
   - 选择 **Ignore query string**

4. 点击右下角的 **Deploy** 生效。

## 如何验证是否设置成功

规则保存后大约需要几十秒生效，你可以这样测试：

1. 打开浏览器开发者工具，切到 **Network** 面板。
2. 在 Emby 客户端或网页端播放一个视频。
3. 找到体积很大、持续加载的视频流请求，常见状态码是 `200` 或 `206`。
4. 查看响应头里的 `cf-cache-status` 字段。

判断方式：

- 如果是 `MISS`，说明当前请求刚开始建立缓存，还在从源站拉取。
- 重新播放同一个视频，或者换另一个账号播放同一个视频时，如果变成 `HIT`，说明这条规则已经生效，后续流量会优先命中 Cloudflare 边缘缓存。

## 使用提醒

- 这类缓存规则更适合视频主流、分片和大体积媒体资源。
- 如果你的上游响应策略比较特殊，建议先挑一个视频做灰度测试，再决定是否全量启用。
- 开启共享缓存前，最好先确认你的访问控制策略不会因为忽略查询参数而被误伤。

# 后续更新教程

这篇文档写给已经部署完成、后面准备继续升级版本的人。

你可以把它理解成一份“更新后的收尾清单”：

- 先判断你这次是怎么更新的
- 再按对应方式完成升级
- 最后做一次数据整理和日志初始化检查

> 如果你只想先把更新流程跑通，记住这一条就够了： `更新 Worker -> 强刷后台 -> 整理 KV / D1 -> 检查 DB / FTS`

------

## 先看你属于哪种更新方式

当前常见的更新方式主要有 2 种：

### 1. 后台快捷更新 Worker

适合你直接在管理后台里上传新的 `worker.js`。

典型路径：



```
全局设置 -> 备份与恢复 -> 快捷更新 Worker
```

### 2. GitHub 推送更新 / Cloudflare 自动部署

适合你通过以下方式更新：

- 推送代码到 GitHub 仓库
- 由 Cloudflare 自动拉取并重新部署
- 或者你自己在 Cloudflare 后台重新部署新代码

这种方式下，通常**不需要再手动上传 `worker.js`**，但更新后的收尾动作依然建议做一遍。

------

## 更新前建议

正式更新前，建议先做这几件事：

1. 在 `全局设置 -> 备份与恢复` 里先导出一份当前配置或完整备份。
2. 记一下你当前的重要环境变量和绑定，例如 `ENI_KV`、`DB`、`ADMIN_PASS`、`JWT_SECRET`、`HOST`、`LEGACY_HOST`。
3. 如果你已经启用了 D1 日志或 FTS5 搜索，更新后记得回到日志页检查初始化状态。

> 如果你是跨大版本升级，或者之前已经积累了不少旧配置，更新后的“整理数据”步骤尽量不要跳过。

------

## 方式一：通过后台快捷更新 Worker

如果你使用的是后台上传 `worker.js` 的方式，可以按下面步骤操作：

1. 进入管理后台。
2. 打开 `全局设置 -> 备份与恢复`。
3. 找到 `快捷更新 Worker`。
4. 上传新的 `worker.js` 文件，等待更新完成。
5. 更新完成后，先不要急着直接操作后台，先执行下面的“更新后必做步骤”。

------

## 方式二：通过 GitHub 推送或 Cloudflare 自动部署

如果你是走 GitHub 或 Cloudflare 自动部署路线，流程会简单一点：

1. 把新版本代码推送到你绑定的仓库分支，或在 Cloudflare 后台重新部署。
2. 等待 Worker 部署完成。
3. 这类方式**不需要再上传 `worker.js`**。
4. 部署完成后，继续执行下面的“更新后必做步骤”。

------

## 更新后必做步骤

无论你是哪一种更新方式，建议都按这个顺序收尾：

### 第一步：强刷后台页面

更新完成后，先在浏览器里强制刷新后台页面。

常见做法：

- Windows：`Ctrl + R` 或 `Ctrl + F5`
- macOS：`Command + Shift + R`

这样可以避免后台还在使用旧版静态资源或旧缓存。

### 第二步：整理 KV 和 D1 数据

进入：



```
全局设置 -> 备份与恢复 -> 一键整理数据
```

建议处理顺序：

1. 先整理 `KV` 数据
2. 再整理 `D1` 数据

这一步的主要作用是：

- 修复旧版本遗留的索引和脏配置
- 清理升级后可能残留的旧键、旧状态和过期数据
- 让新版本读取到更干净的配置结构

### 第三步：检查日志数据库初始化状态

进入：



```
日志记录
```

建议检查这两项：

1. `初始化 DB`
2. `初始化 FTS5`

处理建议：

- 如果你启用了 D1 日志功能，建议检查 `初始化 DB` 是否已经完成
- 如果你开启了全文搜索，或者日志页提示 FTS 未初始化，再执行一次 `初始化 FTS5`

------

## 最简执行版

如果你只想记住最少步骤，可以直接看这里：

### 只用了 KV，没用 D1

1. 更新 Worker
2. 强刷后台页面
3. 整理 `KV` 数据

### 用了 D1，但没开 FTS5

1. 更新 Worker
2. 强刷后台页面
3. 整理 `KV` 数据
4. 整理 `D1` 数据
5. 检查 `初始化 DB`

### 用了 D1，也开了 FTS5

1. 更新 Worker
2. 强刷后台页面
3. 整理 `KV` 数据
4. 整理 `D1` 数据
5. 检查 `初始化 DB`
6. 检查或执行 `初始化 FTS5`

------

## 常见问题

### 1. 为什么更新后页面看起来没变化

大概率是浏览器还在使用旧缓存。

优先做这两件事：

1. 强刷页面
2. 重新登录后台再看一次

### 2. 为什么升级后设置页或节点列表有点异常

常见原因是旧版本遗留的 KV / D1 数据还没有整理。

优先去执行：



```
全局设置 -> 备份与恢复 -> 一键整理数据
```

### 3. 为什么日志搜索提示 FTS 没准备好

这通常说明 FTS5 结构还没有初始化。

进入 `日志记录` 页面后，执行：

- `初始化 FTS5`

------

## 一句话总结

更新时最容易漏掉的，不是“上传文件”，而是“更新后的整理和初始化”。

你只要记住下面这条线就够了：



```
更新 Worker -> 强刷后台 -> 整理 KV / D1 -> 检查 DB / FTS
```

## 部署与初始化

### 为什么部署后打不开后台

优先检查这几项：

- `ADMIN_PASS` 和 `JWT_SECRET` 是否已配置
- `ENI_KV` 是否已正确绑定
- 自定义 `ADMIN_PATH` 是否填写正确
- 当前访问域名是否已经正确接入到 Worker

### 为什么 Cloudflare 联动功能不能用

通常是因为 `cfApiToken`、`cfZoneId`、`cfAccountId` 还没填完整，或者 Token 权限不够。建议先保证代理主链路跑通，再补这些增强能力。

## 升级与整理

### 为什么升级后页面样式或功能不对

最常见原因有两个：

- 浏览器仍在使用旧缓存
- KV / D1 里残留了旧版本的数据结构

建议顺序：

1. 先强刷后台页面
2. 再执行一次 `一键整理数据`
3. 最后回到日志页确认 DB / FTS 初始化状态

## 域名前缀代理

### 为什么 `hk.你的域名` 打不开

优先排查：

- 是否已经配置 `HOST`
- 是否已在后台开启域名前缀代理
- 节点是否确实保存成 `PRE` 模式
- Cloudflare DNS 中是否自动生成了对应记录
- 当前证书与路由是否覆盖该前缀子域

## 日志与搜索

### 为什么日志搜索提示 FTS 没准备好

这通常说明 FTS5 结构还没有初始化。进入 `日志记录` 页面后，执行一次 `初始化 FTS5`，再重新搜索即可。

### 为什么日志页没有数据

常见原因：

- 没绑定 `DB`
- 还没有初始化数据库
- 日志功能未开启
- 刚部署完成，还没有产生可记录的请求
